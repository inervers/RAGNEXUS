项目中的关键技术决策和背后思考。面试官问"为什么选这个不选那个"时，答案在这里。

01为什么用 DeepSeek，而不是 OpenAI / Claude？

不是情怀，是现实考量。

成本
DeepSeek API 价格约为 GPT-4 的 1/20，在大量 Agent 调用场景下差距显著
中文能力
中英混合技术文档问答中不逊于 GPT-4
Function Calling
原生支持工具调用，无需额外适配

当前使用官方模型名 deepseek-v4-flash（旧别名 deepseek-chat 已于 2026-07-24 停用）。智谱 GLM 免费版踩过坑（单并发 + 高峰限流 + 空 content 崩溃），故保留为 fallback。

一个关键坑：LLM 不总是主动调 search_knowledge，所以 /query 端点做了 强制检索注入——先把 query 查知识库，再把结果塞进 system prompt，确保每轮回答都有知识支撑，不依赖模型自己的"意愿"。

02为什么用 ChromaDB，而不是 Milvus / Qdrant？

按实际规模选型，不盲目上分布式。

  • 嵌入式向量数据库，零依赖，进程内运行
  • 当前知识库 700+ chunk，ChromaDB 完全够用，检索延迟 < 50ms
  • 100 万级瓶颈顺序：向量检索延迟（换 HNSW 参数）→ 单机内存（换 Milvus/Qdrant）→ 多路召回吞吐（加缓存层）
迁移路径明确：ChromaDB 数据导出到 Milvus 只需改 collection.query() 那几行，检索逻辑本身框架无关。

03为什么自己造多路召回的轮子，而不是直接上 LangChain？

LangChain 是胶水，不是架构。

  • LangChain 的 ensemble_retriever 的 RRF 实现是硬编码的，调不了 k 值和权重
  • 需要 sparse_weight=2.0 平衡中英文——中文场景 BM25 的 term 匹配比向量更可靠（"动态计算图"这种词，英文语义匹配够用，中文必须 BM25 精确命中）
  • 自实现调试路径透明：出问题知道去查 retrieve() → rrf_merge() → rerank() 哪一步
与 Reranker 的关系：BM25 会拉入噪声（低语义但高关键词匹配的文档），RRF 融合后 Top-10 反而比单路向量差。Cross-Encoder Reranker 做二次精排把噪声压下去，评测数据说明了这一点。

04为什么用滑动窗口限流，而不是令牌桶？

选择标准是"谁先扛不住"。

  • 令牌桶适合突发流量，但 DeepSeek API 不允许突发调用，被限返回 429
  • 滑动窗口严格保证每分钟不超过 N 次，对上游 API 更友好
  • 实现用 collections.deque 存时间戳，O(1) 入队出队，无外部依赖
  • 未来分布式限流会迁移到 Redis + Lua 脚本

05Multi-Agent 为什么是"研究员 → 写作者 → 审核员"三阶段？

解决单次 LLM 调用的三个结构性缺陷。

AGENT 01
研究员
检索知识库 + 提取关键信息，专注精度，不参与生成
AGENT 02
写作者
根据材料组织文章，专注表达
AGENT 03
审核员
检查事实错误和逻辑漏洞，不合格回退重写

为什么不用 Chain-of-Thought：CoT 在单个 prompt 里模拟多步推理，但 LLM 在长上下文中容易"中途掉线"——写到后面忘了前面的约束。Agent 之间的显式状态传递（研究员输出 → 写作者输入）避免了这个问题。

状态驱动机：写作者返回后检查状态，已审核通过就不重复跑，防止写作者 ↔ 审核员死循环。

06检索评测

28 篇技术文档知识库，5 道测试题的三种检索方法对比：

方法Recall@5 平均Recall@10 平均说明
单路向量0.560.56仅依赖语义匹配
混合 + RRF 融合0.600.42BM25 引入噪声，RRF 未有效过滤
混合 + Reranker0.560.58Cross-Encoder 压制噪声，Top-10 略有提升

结论：小规模高质量知识库中单路向量与混合+Reranker 接近；混合+RRF 的 Top-10 Recall 较低。生产级系统采用多路召回+Reranker 的核心原因，是在大规模、含噪声的语料中同时覆盖语义与关键词的检索盲区。
